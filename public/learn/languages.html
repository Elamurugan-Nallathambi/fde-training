Languages, AI SDKs and learning playlists

Which language to build in, how to call any AI provider with the same code, and a playlist to learn or refresh every major language and the DevOps tools around them.

Read first

Choosing a language, and one common pattern for AI SDKs

You will know which language to pick for a POC and why, and how to call any model provider with the same code.

Why this matters on a client engagement

Clients ask which language you will build in, and their team will have to run what you leave behind. The language also changes how much help you get from AI coding assistants and how many ready-made libraries you can use. Picking well on day one saves weeks later.

The language is your choice

There is no single right language. Use the one you know best, or the one the client's team already runs, because they will maintain it after you leave.

One practical bias is worth knowing. AI models and coding assistants learned from public code, and there is far more public Python and JavaScript than most other languages. GitHub's Octoverse 2024 report found that Python became the most used language on GitHub, driven by AI and data work. In practice that means assistants give their most reliable help in Python, then JavaScript and TypeScript, then the other mainstream languages. They still help in Go, Rust, Java or C#; you just check their output a little more closely.

A sensible default for AI work

For a POC that calls models, reads documents and moves data, Python is the default: the model providers, LiteLLM, data tools such as pandas, and most tutorials start there. For a web front end, or when the client's stack is Node.js, use TypeScript; it adds types to JavaScript, which catches mistakes early.

SQL is not optional in any language. Almost every client keeps the truth in a database, so you will read and write SQL whatever else you choose. Bash, the shell, is the glue for setup scripts, automation and CI.

When performance or footprint matter

Pick Go or Rust when a part of the solution must be fast, small or run many requests at once: an API gateway, a high-volume document pipeline, a service on a small device, or a tool that must start instantly. Go is simple to learn and compiles to one binary that is easy to deploy. Rust gives the most speed and memory safety but takes longer to learn.

You do not have to choose one language for everything. A common shape is Python for the AI and data parts and Go or Rust for one hot path, connected by an API. Java and C# are the right call when the client runs on the JVM or .NET and wants code their team can own.

AI SDKs: one common pattern, then provider SDKs when you need them

Every model provider publishes its own SDK: Anthropic, OpenAI and Google each have official libraries for Python, TypeScript and other languages. They are the best place for provider-specific features, and worth exploring when you need one.

For client work, start with a common layer so the provider is a setting, not a rewrite. In Python this course uses LiteLLM, which calls many providers, including local models through Ollama, with one OpenAI-style interface. In TypeScript, the AI SDK by Vercel plays the same role. Keep the model name in configuration, so you can compare providers on the client's own test cases, follow their procurement choice, or move to a self-hosted model later without touching the business logic.

python
import os
from litellm import completion

# Change provider by changing this one setting, never the code:
#   anthropic/claude-sonnet-5-5, openai/<model id>, gemini/<model id>, ollama/llama3.2 (free, local)
MODEL = os.environ.get("LLM_MODEL", "ollama/llama3.2")

reply = completion(model=MODEL, messages=[
    {"role": "system", "content": "Answer in one short sentence."},
    {"role": "user", "content": "What is a forward deployed engineer?"},
])
print(MODEL, "->", reply.choices[0].message.content)

Worked example

Worked example: one script, three providers

A client wants to compare a hosted model with a local one before deciding. You write the script above once.

Run it with LLM_MODEL=ollama/llama3.2 on your laptop (free, nothing leaves the machine), then with LLM_MODEL=anthropic/claude-sonnet-5-5 and the API key in an environment variable, then with an OpenAI model id. The code does not change; only the setting does. Run the same 20 test questions through each and compare quality, speed and cost on one sheet.

Start practicing

Practice 1

Call two providers with the same code

30 min

Goal: See for yourself that the provider is a setting when you use a common SDK.

  1. Install Python 3.10 or newer, then run pip install litellm.
  2. Install Ollama and pull a small local model, for example ollama pull llama3.2.
  3. Save the script from this lesson as hello_model.py and run it with LLM_MODEL=ollama/llama3.2.
  4. If you have an API key for any hosted provider, set it in an environment variable and run the script again with that provider's model string.
  5. Write down, for each run, the answer, how long it took and what it would cost.

Done when: The same script ran against at least two models by changing only LLM_MODEL.

Common mistakes

  • Choosing a language the client's team cannot maintain. The POC becomes yours forever.
  • Hard-coding one provider's SDK calls across the business logic, which makes switching a rewrite.
  • Assuming assistant output in a less common language is as reliable as in Python. Review it more closely.
  • Reaching for Rust or Go before you know there is a speed problem. Measure first.
