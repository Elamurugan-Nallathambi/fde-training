Lesson 0.1

Your learning toolkit and why each piece matters

You will know which tools to install before module 1, what each one does, what it costs, and how to use AI tools safely on your own machine.

Why this matters on a client engagement

A client will say 'can you start on Monday, here is access to our repo'. You will not have time to learn your tools then. This lesson tells you what to set up now, so you can practice every lesson by doing and already have safe habits before anyone trusts you with their systems.

The short version

You will set up seven things: a GitHub account, Git, the VS Code editor, a language runtime (Python 3, plus Node.js), at least one AI coding assistant, a chat app for thinking, and a learning journal repository. Together they let you write small programs, keep a history of your work, get help from AI, and show what you learned.

If you have never used a terminal or a code editor, that is fine. The basics page explained the words. This module walks you through each install in order, and every lesson ends with something you can check yourself.

What each piece is for

Think of it like setting up a new desk at work. Each tool has one job.

  • GitHub account: your online home for code. It stores your repositories (project folders with history) and becomes your public portfolio.
  • Git: the program on your computer that records snapshots of a folder over time, so you can see what changed and undo mistakes.
  • VS Code: a free code editor from Microsoft. You open a folder, edit files, and run commands in its built-in terminal.
  • Python 3: the language used for most labs in this program. You need it to run scripts.
  • Node.js (the version marked LTS, long-term support): a runtime for JavaScript. You need it mainly because some AI tools install through npm, the package manager that comes with Node.js.
  • AI coding assistants: GitHub Copilot inside VS Code, Claude Code and OpenAI Codex. They read your project and help you write, explain and fix code. You only need one to start.
  • A chat app (the Claude app or another one): for thinking out loud, asking questions about a concept and planning before you code.
  • A learning journal repository: a GitHub repository where you write what you learned each day. Lesson 5 sets it up.

What is free and what may cost money

Git, VS Code, Python and Node.js are free. A GitHub account is free. The GitHub CLI (a command line tool for GitHub) is free and open source.

The AI assistants change their plans often, so treat this as a snapshot and check the linked pages before you pay for anything. GitHub's plans page lists a Copilot Free plan with limited chat and agent usage, a Copilot Student plan for verified students, and paid plans. The Claude Code quickstart lists what you need to sign in: a Claude Pro, Max, Team or Enterprise subscription, a Claude Console account (API access with pre-paid credits), or access through a supported cloud provider. The Codex README recommends signing in with a ChatGPT account on a Plus, Pro, Business, Edu or Enterprise plan, and says an API key also works with extra setup; the Codex pricing page also lists a Free plan for quick coding tasks.

Our advice: start with Copilot Free inside VS Code. It costs nothing and is the gentlest start. Add Claude Code or Codex later if you or your employer already pay for a plan.

What AI assistants can do on your machine

A chat app only sees what you paste into it. A coding assistant is different. Copilot in agent mode, Claude Code and Codex can read files in the folder you open, edit those files, and run terminal commands such as installing packages or running tests. That is what makes them useful, and it is also why you need rules.

Each tool asks for your approval before risky actions, depending on its settings. Your job is to read what it wants to do before you say yes, exactly like reviewing a colleague's change before it goes live.

Safety rules from day one

These are the same rules a client's security team will expect.

  • Never open client code or client data with a personal account or a personal AI subscription. On an engagement you use the client's approved tools and accounts only.
  • Never paste secrets into any AI tool or commit them to a repository: passwords, API keys, tokens, customer records. Use placeholders such as YOUR_API_KEY.
  • Read every command before you approve it. If you do not understand it, ask the assistant to explain it first, or say no.
  • Keep all learning work in one dedicated folder, for example a folder named fde in your home folder. Open only that folder in your editor and assistant, never your whole home folder or desktop.
  • Keep your learning journal free of anything private about an employer or client, especially if the repository is public.

Worked example

Worked example: a first week setup for a finance analyst

Priya works in finance and has used spreadsheets for years but never a terminal. She has no paid AI plan. She creates a folder called fde in her home folder, creates a free GitHub account, installs Git, VS Code, Python and the Node.js LTS version, then signs in to Copilot Free inside VS Code.

When Copilot in agent mode offers to run a command to install a package, she reads it first, asks Copilot what it does, and only then approves. She keeps a sample budget spreadsheet she made up herself for practice, not her employer's real numbers. By the end of the week her learning journal on GitHub has five short entries.

Lesson 0.2

Create your GitHub account and learn how Git works

You will have a secured GitHub account, Git set up, and a clear picture of how a change moves from your folder to GitHub.

Why this matters on a client engagement

A client's IT team will ask 'is two-factor turned on for your account?' before they give you access. Their engineers will also read your commit history to judge your work. This lesson sets up your account and Git properly, so your journal, labs and later your portfolio all sit in one trusted place.

The short version

GitHub is a website that hosts repositories. Git is a program on your computer that tracks changes in a folder. You make changes on your machine with Git, then push them to GitHub so they are backed up and visible to others.

In this lesson you create the account, lock it down with two-factor authentication, install Git, tell Git who you are, and sign in from your machine. Module 3 goes deeper into branches and pull requests; here you only need the basic loop.

Create and secure your GitHub account

Go to github.com and sign up with an email address you will keep for years, because this account becomes your portfolio. Pick a professional username; employers will see it.

Then turn on two-factor authentication (2FA). With 2FA, signing in needs your password plus a second proof, such as a code from an authenticator app or a passkey. Follow the GitHub guide 'Configuring two-factor authentication' linked below. When GitHub shows recovery codes, save them somewhere safe, such as a password manager. Without them, losing your phone can lock you out.

Install and configure Git

On macOS, the Git install page lists several options. Two simple ones: run xcode-select --install in Terminal to get Apple's Command Line Tools, which include Git, or run brew install git if you already use Homebrew. On Windows, download Git for Windows from the Git install page and accept the default options. Git for Windows also gives you Git Bash, a terminal where the commands in this program work as written.

Open a new terminal and run git --version. If it prints a version number, Git is installed. Then tell Git your name and email. These are stamped on every commit you make. Use the same email as your GitHub account, or the private noreply address GitHub offers in your email settings if you do not want your address public.

bash
git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global --list

Sign in to GitHub from your machine

To push to GitHub, your computer must prove it is you. There are two easy ways. Option one: install the GitHub CLI (on macOS with Homebrew, brew install gh; on Windows, use WinGet or the installer from the GitHub CLI site), then run gh auth login and follow the prompts. It opens a browser to confirm. Option two: in VS Code, the first time you push or clone, VS Code asks you to sign in with GitHub in the browser.

Either way, you never type your GitHub password into the terminal. That is on purpose: the browser handles the sign-in, including your 2FA.

The mental model: six words

A good way to remember it: commit is saving, push is backing up. You can commit ten times offline and push once when you are back online. Push only to your own repositories during this program.

  • Working folder: the files you see and edit on your machine.
  • Staging (git add): choosing which changed files go into the next snapshot.
  • Commit (git commit): saving that snapshot with a message, on your machine only.
  • Push (git push): sending your commits to GitHub.
  • Pull (git pull): bringing commits from GitHub to your machine, for example ones you made on another computer.
  • Clone (git clone): copying a whole repository from GitHub to your machine the first time.

Worked example

Worked example: your first commit in a scratch folder

This sequence was run in an empty scratch folder. It creates a folder, turns it into a Git repository, adds a README file and commits it. Nothing is sent to GitHub yet, so it is safe to try.

After git status you will see README.md listed as an untracked file, meaning Git sees it but is not tracking it yet. After the commit, git log --oneline shows one line: a short commit id and your message 'Add README'. Recent Git versions may call the first branch main or master depending on your settings; both are fine for now.

bash
mkdir git-practice
cd git-practice
git init
echo "# My first repository" > README.md
git status
git add README.md
git commit -m "Add README"
git log --oneline

Lesson 0.3

Install VS Code and get comfortable in it

You will install VS Code, Python and Node.js, find your way around the editor, and run a script from the built-in terminal.

Why this matters on a client engagement

A client will say 'here is the script that builds our weekly report, it broke yesterday, can you take a look?', often while they watch. You need to open an unfamiliar project, run it and read the error without panic. This lesson gets you comfortable in the editor and terminal where that work happens.

The short version

VS Code is a code editor: like a word processor, but built for code and folders of files. You open a folder, click files to edit them, and run commands in a terminal panel at the bottom. Extensions add features, such as Python support or an AI assistant.

In this lesson you install VS Code, Python and Node.js, learn four parts of the screen, set up a Python virtual environment, and run a small check script that proves your setup works.

Install VS Code, Python and Node.js

Check each one in a new terminal: python3 --version (on Windows, python --version), node --version and npm --version. Each should print a version number.

  • VS Code: download it from code.visualstudio.com and install it like any other app.
  • Python: download a current Python 3 release from python.org. On Windows, the installer has an option to add Python to PATH (the list of places your terminal looks for programs); tick it. On macOS, use the python.org installer, then use python3 in the terminal.
  • Node.js: from nodejs.org, download the version marked LTS. It includes npm, which some AI tools use to install.
  • After installing, close and reopen any terminal so it can find the new programs.

Find your way around

  • Explorer: the file tree on the left. Use File, then Open Folder, and pick your fde folder. Always open a folder, not a single file.
  • Editor: the middle area where files open in tabs.
  • Integrated terminal: open it from the Terminal menu, then New Terminal. It starts inside your open folder, which saves you from typing long paths.
  • Command Palette: press Cmd+Shift+P on macOS or Ctrl+Shift+P on Windows. Type what you want, such as 'Python: Select Interpreter', instead of hunting through menus.
  • Source Control: the branch icon on the left. It shows changed files and lets you stage and commit with buttons, using the same Git you installed.

Extensions to install

Open the Extensions view (Cmd+Shift+X on macOS, Ctrl+Shift+X on Windows) and search by name. Always check the publisher name before you install; copycat extensions exist.

  • Python, published by Microsoft: running, debugging and choosing interpreters.
  • GitHub Copilot: AI help inside VS Code. The VS Code setup guide says to hover over the Copilot icon in the Status Bar and select Use AI Features to sign in. Lesson 4 covers this.
  • Optional: Claude Code (search 'Claude Code', published by Anthropic) and Codex (the OpenAI Codex extension). Both are documented on their official pages linked below. Install them only if you plan to use those assistants.

Virtual environments

A virtual environment (venv) is a private box of Python packages for one project. Without it, every project shares one set of packages, and upgrading one for project A can break project B. Create one per project, in a folder named .venv inside the project.

Create it with python3 -m venv .venv. Activate it on macOS with source .venv/bin/activate, or on Windows PowerShell with .venv\Scripts\Activate.ps1. Your prompt then shows (.venv). VS Code usually notices the new environment and offers to use it; if not, run 'Python: Select Interpreter' from the Command Palette. Add .venv to your .gitignore so it is never committed.

Worked example

Worked example: a setup check script

Create a file named check_setup.py in your fde folder with the code below. Then, in the integrated terminal with your .venv active, run python check_setup.py (or python3 check_setup.py). This script was run on macOS both with and without a virtual environment.

It prints your Python version and warns if it is older than 3.11, the minimum this program uses. It then looks for Git on your PATH and prints its version. If it says Git is NOT FOUND, Git is either not installed or your terminal was opened before the install finished; open a new terminal and try again.

python
import shutil
import subprocess
import sys

print("Python version:", sys.version.split()[0])
if sys.version_info < (3, 11):
    print("Please install Python 3.11 or newer.")

git_path = shutil.which("git")
if git_path is None:
    print("Git: NOT FOUND. Install Git, then open a new terminal.")
else:
    result = subprocess.run(["git", "--version"], capture_output=True, text=True)
    print("Git:", result.stdout.strip(), "at", git_path)

Lesson 0.4

Set up GitHub Copilot, Claude Code and Codex

You will know what Copilot, Claude Code and Codex are, how to install and sign in to the one you pick, and how its approvals keep you in control.

Why this matters on a client engagement

A client will tell you 'our team already uses one of these coding assistants, please work in the same one'. Each tool installs, signs in and asks for permission a little differently. This lesson shows you how all three work, so you can switch to whatever the client uses and stay in control of what it runs.

The short version

All three tools are coding assistants: you describe a task in plain English, and they read your project, propose changes and can run commands. GitHub Copilot lives inside VS Code and other editors. Claude Code (from Anthropic) and Codex (from OpenAI) run in your terminal and also have VS Code extensions.

You only need one to start. Copilot inside VS Code is the gentlest start because it needs no terminal install and has a free plan. Module 3's lesson on coding with an AI assistant teaches how to work with these tools well; this lesson only gets one running.

GitHub Copilot in VS Code

What it is: GitHub's assistant, built into VS Code, with chat, inline suggestions and an agent mode that can edit files and run commands.

Cost: GitHub's plans page lists Copilot Free with limited chat and agent usage, Copilot Student free for verified students, and paid plans. VS Code's setup guide says that if you sign in without a plan, an eligible account is enrolled in Copilot Free.

Set up: hover over the Copilot icon in the VS Code Status Bar, select Use AI Features, and sign in with your GitHub account in the browser.

Claude Code

What it is: Anthropic's coding assistant that runs in your terminal, and also as a VS Code extension.

Cost: the quickstart says you need a Claude Pro, Max, Team or Enterprise subscription, a Claude Console account (API access with pre-paid credits) or access through a supported cloud provider. Check the current plans before you subscribe.

Install (from the official quickstart). macOS, Linux or WSL: curl -fsSL https://claude.ai/install.sh | bash. Windows PowerShell: irm https://claude.ai/install.ps1 | iex. Homebrew and WinGet are also listed. Then open a new terminal and run claude --version. On native Windows the docs recommend Git for Windows, which you installed in lesson 2.

Sign in: cd into your project folder and run claude. It prompts you to log in on first use and completes sign-in in your browser.

OpenAI Codex

What it is: OpenAI's coding agent that runs locally in your terminal, with an IDE extension for VS Code and similar editors.

Cost: the README recommends signing in with ChatGPT to use Codex as part of a Plus, Pro, Business, Edu or Enterprise plan, and says you can also use an API key with extra setup. OpenAI's pricing page also lists a Free plan for quick coding tasks. Check the current limits on that page.

Install (from the official README). macOS or Linux: curl -fsSL https://chatgpt.com/codex/install.sh | sh. Windows: powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex". With Node.js: npm install -g @openai/codex.

Sign in: run codex in your project folder and choose Sign in with ChatGPT.

How approvals keep you in control

Each tool decides when to ask before acting. In Claude Code this is the permission mode: it sets which actions Claude can take without asking, you switch it with Shift+Tab in the terminal, and Plan mode describes what it will do and waits for your approval before changing anything. In Codex, the /permissions command chooses when it can edit files or run commands without asking and shows the active sandbox (the area it is allowed to write to). In VS Code, agents can edit files, run terminal commands and call tools; permission levels and terminal approval settings decide which actions need your confirmation, as the VS Code page on approvals and permissions explains.

While learning, keep the most careful setting: let the tool ask before every file edit and every command. Read each request. If you would not run the command yourself, say no and ask why it is needed.

Worked example

Worked example: a first safe task

Open your learning journal folder (or your fde folder) in VS Code, with nothing private in it. Start your chosen assistant and give it a read-only task first, then a small write task you can easily check.

Good first prompts: 'Explain what is in this folder and what each file is for.' Then: 'Write a README.md that describes this repository as my FDE learning journal, with sections for weekly notes, labs and notes.' Read the proposed file before approving the edit. Then run git diff to see exactly what changed, and commit it yourself.

  • Read-only first: an explanation cannot break anything.
  • Small write second: one file, easy to review.
  • You commit, not the assistant, so you stay the reviewer.
bash
cd ~/fde/fde-learning-journal
claude          # or: codex
# after the assistant writes README.md and you approve:
git diff
git add README.md
git commit -m "Add README written with AI help"

Lesson 0.5

Record your learning in a GitHub journal

You will create a journal repository with a simple structure, a daily entry template and short screen recordings, so your progress becomes something you can show.

Why this matters on a client engagement

A hiring manager or client will ask 'show me something you built and how you fixed it when it broke'. Saying you can do it is not enough, they want proof. This lesson sets up a journal of daily commits, labs and short videos that shows how you learn and explain, and builds the note-taking habit you need for handover on every engagement.

The short version

Create one GitHub repository named fde-learning-journal. Every day you study, add a short entry: what you learned, what you built, what broke and how you fixed it, open questions and links. Commit and push at least once per day you study. Once a week, record a 2 to 5 minute video explaining one lab.

Choose public or private on purpose. Public is good for a portfolio. Private is fine if you prefer, and you can make it public later. Either way, never put employer or client information in it.

Create the repository and its structure

On GitHub, create a new repository named fde-learning-journal, tick the option to add a README, then clone it into your fde folder with git clone and the URL GitHub shows. Then create this structure:

  • README.md: who you are, what this journal is, and a list of weeks with links.
  • weeks/week-01.md, weeks/week-02.md and so on: one file per week, one section per day.
  • labs/: the code and data for each lab, one folder per lab, for example labs/week-01-setup-check/.
  • notes/: short topic notes you will want to find again, such as notes/git-cheatsheet.md.
  • .gitignore: list .venv, .env and any large or private files so they are never committed.

What a good entry looks like

Write for your future self and for a reviewer who has five minutes. Use your own words, not copied text. 'What broke and how I fixed it' is the most valuable part: paste the error message, say what you tried, and what finally worked. That is real debugging evidence.

Files ending in .md use Markdown, a simple way to format text with # for headings and - for lists. GitHub shows it nicely formatted. The template in the worked example uses only those two features.

Record short walkthroughs

Once a week, record a 2 to 5 minute screen recording explaining one lab: what problem it solves, a quick run, and one thing you would improve. Talking through your work is a core FDE skill, and short videos are easy for others to watch.

On a Mac, press Shift, Command and 5 together to open the Screenshot app; its toolbar includes Record Entire Screen and Record Selected Portion. On Windows, open Snipping Tool, select the Record button, then New (or press Windows logo key + Shift + R), choose the area, then Start and Stop. Save the file.

Git is built for text, not large videos, so keep videos out of the repository unless they are small. A simple approach is to upload the video to a storage space you control and paste the link into that week's entry. Check what is on screen before you record: close email, chats and anything private.

From journal to portfolio

After a few weeks, your journal shows a dated history of commits, labs that run, and videos of you explaining them. In interviews you can open an entry and walk through a real problem you solved. Module 8 covers turning your best labs into portfolio projects; the journal is the raw material.

Optionally, when you feel ready, the GitHub Foundations certification covers Git basics, working in repositories and collaborating on GitHub. Check GitHub's page for the exam details and any fee before you book.

Worked example

Worked example: a weekly file template

Copy this into weeks/week-01.md and repeat the Day section for each day you study. Replace the YYYY-MM-DD placeholders with real dates. Keep each section to a few lines; short and honest beats long and polished.

When you finish an entry, run git add weeks/week-01.md, then git commit -m "Week 01 day 1 notes", then git push.

markdown
# Week 01 - YYYY-MM-DD to YYYY-MM-DD

## Day: YYYY-MM-DD

### What I learned
- One idea in my own words, as if explaining it to a colleague.

### What I built
- What I made today and where it lives (for example labs/week-01/).

### What broke and how I fixed it
- The error message, what I tried, what finally worked.

### Questions I still have
- Something I do not understand yet.

### Links
- Lesson, docs page or video I used.
- Recording: link to my 2 to 5 minute walkthrough (if any).

Start practicing

Practice 1

Create your journal and first entry

40 min

Goal: Have a working journal repository with structure and one real entry pushed to GitHub.

  1. Create fde-learning-journal on GitHub with a README, choosing public or private on purpose.
  2. Clone it into your fde folder and open it in VS Code.
  3. Create weeks/week-01.md, labs/ and notes/ (add a short README.md inside labs/ and notes/ so Git keeps the empty folders).
  4. Add a .gitignore listing .venv and .env.
  5. Write your first day entry with the template, including your check_setup.py output under What I built.
  6. Commit and push, then open the repository on GitHub and check the formatting.

Done when: Your repository on GitHub shows the folder structure and a week-01.md entry with today's date.

Practice 2

Record your first walkthrough

30 min

Goal: Practice explaining your work out loud in under 5 minutes.

  1. Close email, chat and anything private on your screen.
  2. Start a screen recording with the Screenshot app (Mac) or Snipping Tool (Windows).
  3. In 2 to 5 minutes, show your journal structure and run check_setup.py, explaining what it checks.
  4. Watch it back once and note one thing to do better next time.
  5. Store the video where you control access and add its link to this week's entry.

Done when: Your week-01.md has a working link to a recording of 5 minutes or less.

Common mistakes

  • Writing only what you learned and skipping what broke. The fixes are the most valuable evidence.
  • Putting employer, client or personal data in a public journal. Assume anything public is public forever.
  • Committing large video files into the repository. Link to them instead.
  • Saving entries for the weekend. Small daily commits show steady progress and are easier to write.
  • Copying text from docs instead of explaining in your own words.

Check yourself

  1. What are the five headings in a daily entry, and which one matters most?
  2. Why should videos usually be linked rather than committed?
  3. What should you check on your screen before you start recording?
  4. How does a journal with daily commits help in an interview?
  5. What goes in .gitignore for this repository, and why?
