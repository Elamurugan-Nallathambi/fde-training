Lesson 8.1

Where AI belongs: code, model or human

You will be able to walk a real workflow step by step and decide which steps need plain code, which need a model and which need a person.

Why this matters on a client engagement

A client says 'put AI on our whole quality review process'. Most of those steps are rules a few lines of code can handle, and a few need judgment or a person's sign-off. This lesson helps you split the work that way, so the model only sits where it earns its cost and risk.

The short version

Any workflow is a chain of steps. For each step ask one question: what kind of work is this? If the step follows a fixed rule that you can write down (look up a supplier id, check that a total matches a purchase order, send a file to a folder), it is deterministic code. If the step needs reading or writing messy human language (work out what kind of document this is, pull the invoice number out of a scanned PDF, draft a polite reply), it is a job for a model. If the step carries real risk or cannot be undone (pay money, reject a claim, change a customer record), a person approves it.

In practice, when you classify a ten-step process honestly, often only a few steps need a model. The rest is ordinary software that has been missing for years: an inbox rule, an API call, a lookup table. That is good news. Code is cheap, fast, testable and gives the same answer every time.

Why 'send everything to the model' fails

A tempting design is one big prompt: forward every email to the model, attach every file, and ask it to figure out what to do. It demos well on five friendly examples. On real volume it fails in three ways. Cost grows with every token you send, including steps that a single line of code could do for free. Errors grow because each model call has some chance of being wrong, and chaining many calls multiplies those chances. Debugging becomes almost impossible because you cannot tell which part of the long prompt caused the bad decision.

Splitting the work keeps each model call small and focused. A small, focused call is easier to test with an evaluation set (module 9), easier to swap for a cheaper model later, and easier to explain to the client's risk team.

How to classify a step

Walk the workflow with the person who does it today, as you learned in discovery. For each step write down the input, the output, who does it and how long it takes. Then apply these tests in order.

  • Can I write the rule as if/else, a lookup or an API call? Then it is code, even if a person does it by hand today.
  • Does the input arrive as free text, images or mixed formats that a rule cannot parse reliably? Then a model reads it and returns structured fields.
  • Is the output a judgment (category, priority, likely reason) that a person would make by reading? Then a model can propose it, with a confidence value.
  • Would a wrong answer cost money, break a law or upset a customer, and is it hard to undo? Then a person approves it, at least until the evidence says otherwise.
  • Does the knowledge live only in one person's head? Then write it down as rules first. Many 'exceptions' turn out to be five or six rules nobody had written.

Hidden rules and the expert in the room

In most messy processes there is one experienced person who knows that supplier X always sends credit notes as screenshots, or that orders from one region need an extra check. These exceptions are not written anywhere. Before you hand them to a model, try to capture them as explicit rules in a small table the client can edit. A rule in a table is visible, testable and cheap. A rule buried in a prompt is invisible to the client and can silently stop working when the model changes.

Keep a short list of exceptions you could not turn into rules. Those are the real candidates for model judgment, and they also become test cases for your evaluation set.

Worked example

Worked example: classifying a 10-step intake process

A distribution company receives supplier documents by email from more than 40 senders. They arrive as PDFs, phone screenshots, spreadsheets and forwarded threads. One accounts clerk knows which suppliers are 'difficult'. Here is the process as she describes it, with a decision for each step.

The result is three model steps, six code steps and one human gate. The model only touches the steps where text is messy or a draft is needed. Everything the model produces passes through code checks before a person or the ERP sees it. When you present this to the client, the person who owns the process can see exactly where AI is used and why.

  • Step 1, read the shared inbox: code. Use the mail system's API on a schedule.
  • Step 2, identify the supplier: code. Match the sender address and domain against the supplier master list. Unknown senders go to a person.
  • Step 3, save attachments and get text: code. Use a PDF text library or an OCR service; this is a tool call, not judgment.
  • Step 4, decide if this is an invoice, credit note, statement or something else: model. Formats vary too much for rules.
  • Step 5, extract supplier, invoice number, date, lines and total into a fixed JSON schema: model, followed by validation.
  • Step 6, check totals add up and match the purchase order: code. Arithmetic and lookups should never be left to a model.
  • Step 7, apply known exceptions from the clerk (for example, supplier X always rounds totals): code, from a rules table she can edit.
  • Step 8, write a query to the supplier explaining a mismatch: model drafts it.
  • Step 9, approve the mismatch handling and send the draft: person. It goes to a supplier and may affect payment.
  • Step 10, post the matched invoice to the ERP and write an audit record: code.

Practice 1

Classify a workflow you know

40 min

Goal: Practice deciding code, model or human for every step of a real process.

  1. Pick a process you know from work or daily life, such as expense claims, job applications or customer refund requests.
  2. Write it as 8 to 12 numbered steps in a spreadsheet with columns: step, input, output, who does it today.
  3. Add a column 'type' and mark each step code, model or human using the tests in this lesson.
  4. Add a column 'why' with one sentence per decision, and a column 'hidden rules' for any exceptions only an expert knows.
  5. Count how many steps you marked model. If it is more than half, challenge each one: could a rule or lookup do it?

Done when: You have a sheet where every step has a type and a one-sentence reason, and fewer than half of the steps are marked model.

Common mistakes

  • Starting from the model instead of the workflow. Map the process first, then decide where a model fits.
  • Letting the model do arithmetic, date math or lookups. These are code and should be exact.
  • Hiding business rules inside a long prompt where the client cannot see or change them. Keep rules in a table.
  • Marking every step 'human approval' out of caution. Place gates where risk is real, or people will approve without reading.
  • Forgetting unknown cases. Every classification step needs a path for 'none of the above'.

  2. Why does one big prompt that 'does everything' become expensive and hard to debug?
  3. Give two examples of steps that look like AI work but should be plain code.
  4. What do you do with exceptions that live only in one person's head?

Lesson 8.2

Designing for the unhappy path

You will be able to design an AI step so bad output, failed calls and odd inputs get caught, retried or sent to a person instead of breaking things.

Why this matters on a client engagement

The finance team says 'it worked in the demo, but last week a supplier changed their invoice layout and it all fell over'. Real data is messy and calls fail at the worst time, like month end. This lesson shows you how to plan for those cases up front, so the system fails safely and people keep trusting it.

The short version

Treat every model output as untrusted input. Ask for JSON in a defined schema, not free text. Validate it in code, both its shape and its business rules. If a call fails for a temporary reason, retry it with a growing wait. If it keeps failing or the output is invalid or low confidence, route the case to a person with a clear reason. Make every write idempotent, which means doing it twice has the same effect as doing it once, so a retry never creates a duplicate payment or ticket.

None of this is special to AI. It is the same defensive design used for any unreliable network service. The difference is that a model can fail in a new way: it can return something that looks correct but is not.

Build a failure modes catalogue

Before writing more code, list how each step can fail. Use a simple table: failure, how you detect it, what the system does. Fill it from your discovery notes and from the first test runs. Typical entries are below. The catalogue becomes your test plan and, later, the cases you add to the evaluation set in module 9.

  • Transient errors: timeouts, rate limits, server errors from the model or another API. Detect by error type or status code. Retry with backoff.
  • Invalid output: not JSON, missing fields, wrong types, extra text. Detect by validation. Retry once with the error message, then route to a person.
  • Valid but wrong: correct shape, wrong value, for example a total that does not match the line items. Detect with business rules and cross-checks against source data.
  • Low confidence or unknown case: the document fits no known type. Detect by a confidence field or an 'other' category. Route to a person.
  • Bad input: empty file, unreadable scan, wrong language, a password-protected PDF. Detect before calling the model and skip the call.
  • Downstream failure: the ERP or CRM rejects the write. Detect by its response. Do not lose the item; queue it and alert.

Validate shape, then meaning

Shape validation checks that the output parses and has the right fields and types. Pydantic does this well: you define a class with typed fields and call model_validate_json, and it raises a clear error when something is off. For a small script, a hand-written check like the one in the example is fine and has no dependencies.

Meaning validation checks business rules: totals are not negative, the category is in the allowed list, the date is not in the future, the invoice number appears in the source text. These rules catch the 'looks correct but is not' failures that a schema cannot. Keep the rules in code, give each a clear message, and return all problems at once so the reviewer sees the full picture.

Retries, fallbacks and idempotency

Retry only errors that may succeed next time, such as timeouts and rate limits. Do not retry a validation error forever; the same input will usually fail the same way. Use exponential backoff: wait about 1 second, then 2, then 4, plus a small random amount called jitter so many workers do not retry at the same moment. Stop after a fixed number of tries. Official SDKs often retry some errors for you, so check before adding your own loop on top.

A fallback is what you do when the main path fails: try a second model, use a simpler rule-based result, or hand the case to a person. The safest fallback in most client work is a person with all the context attached.

Idempotency matters because retries repeat work. Give each item a stable key, such as the email message id plus attachment name, and check it before writing. Many APIs accept an idempotency key header for exactly this reason. Without it, a timeout after a successful write can make your retry post the same invoice twice.

Routing to a person well

Sending a case to a person is not a failure; it is the design working. Make it useful: put the case in a queue the team already uses, include the original input, the model output, and the exact list of problems found. Track how many cases go to people and why. If one reason dominates, that is your next improvement. Over time the share of automatic cases should grow because you fixed causes, not because you lowered the bar.

Worked example

Worked example: validate and route model output

This script uses only the Python standard library. It takes five outputs like a model might return for supplier documents and decides for each one whether it can go through automatically or needs a person. It runs as written with python3.

Running it prints 'auto' for the first output and a 'human review' line with a reason for each of the other four: a total sent as text, an unknown document type, low confidence, and a reply with chatty text around the JSON. In a real system, the reason string goes into the review queue so the person knows what to look at. With Pydantic you would replace check() with a model class and its validators; the routing idea stays the same.

python
import json

ALLOWED = {"invoice", "credit_note", "statement", "other"}
REQUIRED = {"doc_type": str, "supplier": str, "total": (int, float), "confidence": (int, float)}

def check(raw: str) -> list[str]:
    try:
        data = json.loads(raw)
    except json.JSONDecodeError as err:
        return [f"not valid JSON: {err.msg}"]
    if not isinstance(data, dict):
        return ["output is not a JSON object"]
    problems = [f"missing or wrong type: {k}" for k, t in REQUIRED.items()
                if not isinstance(data.get(k), t)]
    if not problems:
        if data["doc_type"] not in ALLOWED:
            problems.append(f"unknown doc_type: {data['doc_type']}")
        if data["total"] < 0:
            problems.append("total is negative")
        if data["confidence"] < 0.8:
            problems.append("low confidence")
    return problems

def route(raw: str) -> str:
    problems = check(raw)
    return "auto" if not problems else "human review: " + "; ".join(problems)

outputs = [
    '{"doc_type": "invoice", "supplier": "Acme Ltd", "total": 1240.5, "confidence": 0.93}',
    '{"doc_type": "invoice", "supplier": "Acme Ltd", "total": "1,240.50", "confidence": 0.9}',
    '{"doc_type": "receipt", "supplier": "Beta Co", "total": 80, "confidence": 0.95}',
    '{"doc_type": "statement", "supplier": "Gamma", "total": 0, "confidence": 0.55}',
    'Sure! Here is the JSON you asked for: {"doc_type": "invoice"}',
]
for raw in outputs:
    print(route(raw))

Write a failure catalogue and test it

60 min

Goal: Turn 'what could go wrong' into checks that actually run.

  1. Copy the example script into a file and run it with python3 to see the five routing decisions.
  2. In a spreadsheet, list at least eight ways a document intake step could fail, with columns: failure, how to detect, action.
  3. Add two new rules to check() from your list, for example the supplier must not be empty and the total must be under a set limit.
  4. Add three new sample outputs to the list that trigger your new rules, and run the script again.
  5. Ask a free LLM chat to return JSON for a messy invoice text you write, paste its reply into the list, and see how it is routed.

Done when: Your script routes at least eight sample outputs, each new rule fires at least once, and every row in your catalogue has an action.

Common mistakes

  • Trusting output because it parsed. A valid schema can still hold wrong values; add business rules.
  • Retrying everything, including validation errors, until you hit rate limits and cost spikes.
  • Retrying writes without an idempotency key, which creates duplicates after a timeout.
  • Sending cases to a person with no reason attached, so reviewers redo the whole task.
  • Hiding failures in logs nobody reads. Count them by reason and review the counts every week.

Check yourself

  1. Name four types of failure in an AI step and how you would detect each.
  2. Which errors should you retry, and why add jitter to backoff?
  3. What does idempotent mean, and how would you make an invoice posting idempotent?
  4. What should a person receive when a case is routed to them?

Lesson 8.3

Agentic system design: from a vague ask to production

You will be able to take a vague ask like 'use AI in our factory', ask the right questions and talk through an MVP and a production design in a clear order.

Why this matters on a client engagement

An operations head says 'we want to use AI in our plant, where do we start?'. There is no spec, just a wish, and FDE interviews test the same thing. This lesson gives you an order to work in, from questions to bottleneck to MVP to production, so you find the real problem and name the trade-offs out loud.

The short version

Work in this order and think out loud. Clarify the ask. Find the real bottleneck. Agree requirements and one success measure. Propose the smallest useful MVP. Only then describe the production design: model, agent loop, tools and permissions, context and memory, evaluation, observability, cost, security, and deployment. Saying your reasoning aloud lets the client or interviewer correct you early, which is cheaper than being wrong late.

Step 1 to 3: clarify, find the bottleneck, define success

Start with questions, not boxes. Who is the user? What happens today, step by step? Where does time or money actually go? What data exists and who owns it? What are the rules (privacy law, safety, union agreements)? What must never go wrong? What would make the sponsor say this worked?

Take the hospital example. 'Waiting time' could mean triage, waiting for a doctor, waiting for test results, or waiting for a bed upstairs. Each has a different cause. If questions reveal that patients wait mostly for a bed because discharge paperwork is slow, the AI opportunity may be drafting discharge summaries for a doctor to approve, not a chatbot in the waiting room. Write the bottleneck as one sentence and one success measure, for example 'median time from discharge decision to bed released, measured weekly'.

Step 4: a simple MVP

The MVP is the smallest thing that proves value on real data with a person in control. For the hospital: a tool that drafts discharge summaries from existing notes for one ward, which a doctor edits and signs. No autonomous actions, no new systems, one integration to read notes. State what is out of scope. A small MVP that works beats a large plan that never ships, and it gives you the evidence to fund the next step.

Step 5: the production design

Walk through the parts below. You do not need to be exhaustive on each; you need to show you have thought about each and know where the risks sit.

  • Model choice: start with one provider's strongest suitable model to prove quality, then move cheaper models onto simple subtasks such as classification once your evals show they hold up.
  • Harness and agent loop: the code that calls the model, runs the tools it asks for, feeds results back, and stops on a clear condition or step limit. Prefer a fixed workflow when the steps are known; use an agent loop only when the path truly varies (module 7).
  • Tools and permissions: each tool does one thing with clear inputs. Read tools are open; write tools are narrow, logged and often need approval. The agent never gets more access than the user it acts for.
  • Context and memory: what goes into each call (task, relevant documents, recent steps) and what is stored between runs (case history, user preferences). Keep context small and relevant; more is not better.
  • Evals: a golden set of real cases with expected results, run on every change (module 9).
  • Observability: a trace per run showing each model call, tool call, input, output, cost and time, so you can answer 'why did it do that?'.
  • Cost: estimate tokens per case times volume, then cut with caching, smaller models and fewer calls.
  • Security: prompt injection from documents or emails, jailbreak attempts, personal data masking, least privilege for tools, and a plan for model failures: what the system does when the model is down, slow or wrong. Usually it falls back to the manual process, never to an unsafe action.
  • Deployment: where it runs, how it is updated, who is on call, and how it rolls out (next lesson).

Worked example

Worked example: answer outline for 'use AI in our factory'

Here is how a strong answer might run, in about the order you would say it. It is an outline, not a script; the point is the sequence and the reasons.

Notice what the answer does not do: it does not start with a model name or a vector database. It earns the design by first finding a narrow, measurable problem.

  • Clarify: 'What does the factory make, what slows it down today, and who would use the tool? Is there a recent problem that triggered this request?' Suppose the answer is: unplanned machine stops, and technicians spend a long time finding the cause in manuals and old maintenance tickets.
  • Bottleneck: 'Time from a machine fault to the right fix is long because knowledge is spread across manuals, tickets and a few senior technicians.'
  • Success measure: 'Median time to repair for the top 20 fault codes on one line, compared with the last three months.'
  • MVP: 'A fault assistant for one production line. A technician enters the fault code and symptoms; the system searches manuals and past tickets and suggests likely causes with sources. The technician decides. Nothing is written to machines.'
  • Production design: one model family to start; a fixed workflow of retrieve then answer, with an agent loop only for follow-up questions; read-only tools for manuals, ticket history and sensor readings; context limited to the matched fault code; memory as the ticket history itself, updated by the technician's confirmed fix.
  • Evals and traces: 100 past faults with known fixes as the golden set; pass rate on 'right cause in top three'; a trace for every query.
  • Security and failure: no write access to equipment; mask employee names in tickets; if the model is down, the technician uses the manual as today; injection risk is low because sources are internal, but documents are still treated as data, not instructions.
  • Cost and rollout: estimate queries per shift, start with shadow use by two senior technicians, then widen.

Lesson 8.4

Integrate with what exists and roll out safely

You will be able to plan how an AI solution plugs into the client's current systems and moves to production in small, low-risk steps.

Why this matters on a client engagement

The sponsor says 'we are not moving off our ERP, and nothing can break month-end close'. Their name is on the project if it goes wrong. This lesson shows you how to build on the systems the team already uses and roll out step by step with evidence, so the sponsor can say yes safely.

The short version

Leave the system of record where it is. Read from it and write back to it through its official API or import, so people keep working in the screens they know. Then roll out in rungs: a test environment, shadow mode, assisted mode with approval, more autonomy for low-risk cases, and finally production. Keep an audit trail and agent traces from day one so anyone can see what the agent did and why. Report results in business terms: cost saved, risk reduced, revenue gained.

Build on top, not instead

Most companies run on a few core systems: an ERP for finance and orders, a CRM for customers, a ticketing tool for support or IT. They hold the official data, the permissions and the audit history. Your AI component should sit beside them. For example, the invoice assistant reads new invoices from the ERP's inbox queue and writes a suggested match back as a draft that a clerk confirms in the ERP screen.

This approach is close to what Martin Fowler calls the strangler fig pattern: you add new capability around the old system one piece at a time, instead of replacing it in one go. Each piece can be switched off without breaking the rest. Use feature toggles (on/off settings in configuration) so you can turn the AI step off per team or per supplier in minutes if something goes wrong.

The rollout ladder

Each rung has an entry condition, usually a pass rate on your evaluation set or on real cases, and an exit condition agreed with the sponsor. Move up only with evidence, and be ready to move down.

  • Test environment: run on copies or samples of real data. Nothing reaches real users. Goal: the system works end to end and passes the golden set.
  • Shadow mode: the AI runs on live cases alongside the people doing the work, but writes nothing. You compare its output with what people actually decided. This is sometimes called a dark launch. Goal: measured agreement on real traffic.
  • Assisted mode: the AI's output appears as a suggestion or draft, and a person approves, edits or rejects it. Every decision is logged. Goal: high approval rate with few edits.
  • Increasing autonomy: for clearly low-risk cases (for example invoices under a set amount from known suppliers that match the PO exactly) the system acts on its own, while everything else stays assisted. Widen the low-risk band only as evidence grows.
  • Production: the agreed scope runs as normal operations, with monitoring, alerts, an owner and a way to switch back to manual.

Audit trail and traces

An audit trail records business decisions: which case, what the AI suggested, who approved it, what was finally done, and when. A trace records the technical path of one run: each model call with its prompt and output, each tool call, timings and cost. Tools such as Langfuse or the tracing built into agent SDKs capture traces for you. Together they let you answer the two questions every client will ask after an incident: what did the agent do, and why. Module 9 covers the audit table and monitoring in more detail.

Measure in the three business buckets

Sponsors fund outcomes, not models. Put every result in one of three buckets. Cost saved: hours of manual work removed, overtime avoided, fewer contractor hours. Risk reduced: fewer errors reaching customers or the ledger, faster detection of fraud or compliance issues, a complete audit trail. Revenue gained: faster quotes, fewer lost orders, quicker onboarding of new customers. Measure a baseline before you start, use the same measure after, and state your assumptions in plain words.

Many engagements start with a paid discovery or audit phase before any build. The output is an operating map of the client's workflows and a value versus effort priority matrix: each candidate use case placed by how much it is worth and how hard it is. The top-right quick wins become the first rollout.

Worked example

Worked example: rolling out an invoice assistant

A mid-sized company wants to speed up invoice matching. The finance director is the sponsor. Their ERP stays the system of record. Here is a rollout plan written in the language the sponsor will read. The numbers are an example of how you would state targets, not results from a real project.

Every stage has an exit decision written down before it starts. That turns 'do we trust the AI?' from a feeling into a check against agreed evidence, which is what lets the sponsor say yes.

  • Discovery: map the invoice process with two clerks, measure the baseline (for example, average minutes per invoice and the share of invoices with errors found later).
  • Test: run the assistant on last quarter's invoices in a copy of the data. Target agreed with the sponsor, for example 90 percent correct matches on the golden set.
  • Shadow, 2 weeks: on live invoices the assistant produces a match; clerks work as usual. Compare daily. Review every disagreement and add the interesting ones to the golden set.
  • Assisted, 4 weeks: the suggested match appears as a draft in the ERP. Clerks approve or edit. Track approval rate, edit reasons and minutes per invoice.
  • Low-risk autonomy: exact three-way matches under a set amount from known suppliers post automatically, with a daily sample checked by a clerk.
  • Report: cost saved (clerk hours), risk reduced (errors caught before payment), revenue effect (early payment discounts captured), each against the baseline.

Lesson 8.5

Example portfolio projects and a 30-day build plan

You will be able to pick, build and write up one end-to-end portfolio project that shows real FDE skills, following a four-week plan.

Why this matters on a client engagement

A hiring manager asks 'show me something you built for a messy real problem, not a tutorial'. A chatbot or to-do app does not answer that. This lesson helps you plan one deep project that handles real data, is measured and is explained like you would to a sponsor.

The recipe for one strong project

Follow these steps. Each one maps to a skill from this program, so the finished project is evidence of the whole job, not just coding.

  • Pick an industry you care about or know: healthcare, finance, legal, logistics, HR, manufacturing. Interest keeps you going when the data gets ugly.
  • Find messy public data, then add synthetic data where real data is private. The Python library Faker generates realistic names, addresses and dates.
  • Pick ONE real bottleneck in that industry, written as one sentence, the way you would after discovery.
  • Build an agent or workflow that removes that bottleneck, using the code, model or human split from lesson 1.
  • Connect it to real infrastructure: a real Postgres database, and at least one external API with real authentication (an API key or OAuth), not just local files.
  • Handle edge cases: schemas, validation, retries and a human review path (lesson 2).
  • Wrap it in an eval harness: a golden dataset of 30 to 100 cases and a pass rate you rerun after every change (module 9).
  • Deploy it in a container on a cloud service so others can try it, not only on your laptop.
  • Write it up like an FDE: a scoping document, the trade-offs you made, what broke and how you fixed it, and what you would standardize to run it for ten customers.

Where to find data

Use well-known public sources and always read the licence. Data.gov lists US government datasets on transport, health, finance and more. Hugging Face Datasets and the UCI Machine Learning Repository host many text and tabular datasets. Some sources fit specific briefs well: the Consumer Complaint Database from the US Consumer Financial Protection Bureau has real complaint text with product and issue labels; the CUAD dataset from The Atticus Project has commercial contracts with labelled clauses; ClinicalTrials.gov publishes trial records with eligibility criteria as free text. Real data gives you real mess; synthetic data lets you plant known edge cases for your golden set.

The 30-day plan

Plan about an hour or two a day. Each week ends with something you can show.

  • Week 1, complete one real loop: the agent loop or workflow, two or three tools, basic guardrails (allowed actions, step limit), the context it needs, simple memory such as case history in Postgres, and an audit trail table. One case should go from input to result end to end.
  • Week 2, make it recover: JSON schemas for every model output, validation, a failure modes catalogue, exception handling, and a review queue for cases it cannot handle.
  • Week 3, make it measurable and affordable: retries with backoff, a golden dataset with a pass rate, cheaper models for simple subtasks where evals allow, cost per case, and an estimate of time, risk or revenue effect against a baseline.
  • Week 4, defend it: deploy it, then rehearse two talks. As the engineer: architecture, decisions and trade-offs. As the sponsor: problem, outcome, evidence, risk. Show it to a few real business people from that industry and write down their feedback.

What the write-up must show

Keep it short and honest: a one-page scoping document (problem, user, success measure, out of scope) and a system diagram. A table of trade-offs, for example 'used a fixed workflow instead of an agent loop because the steps never change'. A 'what broke' section with two or three real failures and fixes. Eval results with the pass rate and the main failure reasons. Finally, 'running it for ten customers': what you would make configurable, what you would monitor, and what onboarding a new customer would take. That last section shows product thinking.

Worked example

Worked example: eight project briefs

Each brief lists the industry, the bottleneck, a data idea, what the agent does, where a person approves, and how you measure it. Pick one, and narrow it further if you can. Check each data source's licence before you use it.

  • Accounts payable invoice exception triage (finance). Bottleneck: clerks spend hours on invoices that do not match the PO. Data: synthetic invoices, POs and supplier records generated with Faker, with planted mismatches. Agent: extracts fields, runs the match in code, explains the mismatch and drafts a supplier query. Human: approves any hold or supplier email. Eval: correct exception reason on a golden set of planted mismatches.
  • Insurance claims intake (insurance). Bottleneck: claim forms and photos arrive incomplete and staff chase missing details. Data: synthetic claim forms and emails made with Faker. Agent: extracts claim fields, checks policy rules in code, lists missing items and drafts a request. Human: approves any decline or payment step. Eval: missing-item detection rate and field extraction accuracy.
  • Clinical trial eligibility extraction with PII masking (healthcare). Bottleneck: coordinators read long eligibility criteria by hand. Data: trial records from ClinicalTrials.gov plus synthetic patient notes. Agent: masks names and identifiers, extracts structured inclusion and exclusion criteria, and flags likely matches. Human: a coordinator confirms every match. Eval: criteria extraction accuracy and zero unmasked identifiers in outputs.
  • Contract clause review (legal). Bottleneck: lawyers scan every contract for a short list of risky clauses. Data: the CUAD dataset of labelled contract clauses. Agent: finds and quotes target clauses, compares them to a standard playbook and marks deviations. Human: a lawyer accepts or rejects each flag. Eval: clause found and correctly labelled against CUAD labels.
  • Customer complaint routing with knowledge-base answers (financial services support). Bottleneck: complaints sit in a general queue before reaching the right team. Data: the CFPB Consumer Complaint Database text and labels. Agent: classifies product and issue, routes the case, and drafts a reply from a small knowledge base you write. Human: approves every reply sent to a customer. Eval: routing accuracy against the dataset labels and reviewer approval rate of drafts.
  • Logistics delay explanation and customer updates (logistics). Bottleneck: customer service cannot quickly explain why a shipment is late. Data: transport datasets found on Data.gov plus synthetic orders and shipment events. Agent: reads shipment events, explains the likely delay cause in plain words and drafts a customer update. Human: approves updates for key accounts. Eval: correct delay cause on planted cases and draft approval rate.
  • HR policy assistant (HR). Bottleneck: HR answers the same policy questions every day. Data: a set of policy documents you write, modelled on public examples, plus synthetic employee questions. Agent: answers with quotes from the policy and refuses when the answer is not in it. Human: HR reviews any answer about pay, leave disputes or discipline. Eval: answer correctness and correct refusal rate on a golden question set.
  • Sales call notes to CRM updates (sales). Bottleneck: reps skip CRM updates after calls. Data: synthetic call transcripts you write or generate, with a mock CRM in Postgres. Agent: extracts next steps, deal stage and contacts, and proposes CRM field changes. Human: the rep approves the changes. Eval: field-level accuracy against the expected updates.

Lesson 8.6

Preparing for FDE interviews

You will know the usual shape of FDE hiring loops and have a practice plan for each round, including live Python without an IDE and questions on your own project.

Why this matters on a client engagement

A recruiter says 'the loop has coding, a system design round, a client scenario and a deep dive on your project'. People who only practise algorithm puzzles get caught out. This lesson shows you what each round tests and how to prepare, and that practice makes you better at the real job too.

The common shape of the loop

Loops differ between companies, but candidates commonly report three kinds of round, sometimes with a take-home assignment as well. A behavioral round asks about ownership and communication: a time you owned a problem end to end, handled an unhappy customer, or changed course after being wrong. A technical deep dive covers coding and system design, often agentic system design as in lesson 3, plus questions about AI security. A case study round gives you a vague client problem and asks you to scope it aloud: questions, bottleneck, MVP, success measure, risks.

Expect deep questions about your own projects in any round. Interviewers pick one decision and keep asking why. This is where the portfolio project from lesson 5 pays off, if you built it yourself and wrote down the trade-offs.

Object-oriented Python, for real

OOP questions are rarely 'define polymorphism'. More often you are asked to design 30 to 50 lines of clean classes that hold state and enforce rules: a rate limiter, a ticket queue with priorities, an inventory that cannot go negative, a simple bank account with a transaction history. Interviewers look for clear names, small methods, state that cannot be put into an invalid condition, sensible errors, and a short demo that shows it works.

Know the standard library pieces that make this easy: dataclasses for simple record classes, heapq for priority queues, collections.deque for sliding windows, enum for fixed choices, and typing hints. The example shows a ticket queue in under 40 lines.

Live coding in a plain editor

Some loops ask you to write Python in a shared document or plain text editor, with no syntax highlighting, no autocomplete and no way to run it. The point is to see whether you can write correct code from memory. Know your imports exactly (from dataclasses import dataclass, field; import heapq), write real code rather than pseudocode, and trace through it by hand with a small input before saying you are done. Talk while you write: say what each class is for and what case you are handling.

Take-home assignments are also common. A typical form is: clone a repository, fix a few issues, and record a short video explaining what you changed and why. They are judged on production readiness (tests, error handling, clear commits, no secrets in code) and on communication. A clear five-minute video that explains trade-offs often matters as much as the code.

AI security and soft skills

Be ready to explain prompt injection (instructions hidden in data the model reads, such as an email that says 'ignore your rules'), jailbreaks (users trying to make the model break its rules), PII protection (masking, access control, retention), and how the system behaves when the model fails or is unavailable. Good answers name concrete controls: treat retrieved content as data, narrow tool permissions, validate outputs, human approval for risky actions, and a manual fallback.

Soft skills are tested throughout, not only in the behavioral round. Interviewers watch for customer empathy, ownership of the outcome rather than the task, breaking a vague problem into parts, product sense (what is worth building), comfort with ambiguity, and explaining a technical decision to a non-engineer in plain words. Prepare five short stories from your own experience that show these, each with the situation, what you did, and the result.

Worked example

Worked example: a ticket queue with priorities

This is the kind of class design an interviewer might ask for: 'Build a support ticket queue. Urgent tickets come first; tickets with the same priority are served in arrival order; the same ticket must not be queued twice.' It runs as written with Python 3.11 and prints ['T2', 'T3', 'T1'] None.

Points to say aloud while writing it: the Ticket dataclass orders by rank then by an increasing sequence number, which keeps equal priorities first in, first out; the queue rejects unknown priorities with a clear error; a set of open ids makes add idempotent; pop returns None when empty instead of raising. Then mention what you would add next: a peek method, tests with unittest, and a lock if several threads use it.

python
import heapq
import itertools
from dataclasses import dataclass, field

PRIORITY = {"urgent": 0, "high": 1, "normal": 2, "low": 3}

@dataclass(order=True)
class Ticket:
    rank: int
    seq: int
    ticket_id: str = field(compare=False)
    title: str = field(compare=False)

class TicketQueue:  # most urgent first; equal priority is first in, first out
    def __init__(self) -> None:
        self._heap: list[Ticket] = []
        self._counter = itertools.count()
        self._open: set[str] = set()

    def add(self, ticket_id: str, title: str, priority: str = "normal") -> None:
        if priority not in PRIORITY:
            raise ValueError(f"unknown priority: {priority}")
        if ticket_id in self._open:
            return  # same ticket sent twice: ignore it
        self._open.add(ticket_id)
        heapq.heappush(self._heap, Ticket(PRIORITY[priority], next(self._counter), ticket_id, title))

    def pop(self) -> Ticket | None:
        if not self._heap:
            return None
        ticket = heapq.heappop(self._heap)
        self._open.discard(ticket.ticket_id)
        return ticket

q = TicketQueue()
for tid, title, prio in [("T1", "Printer jammed", "low"), ("T2", "Payroll failed", "urgent"),
                         ("T3", "VPN slow", "normal"), ("T2", "Payroll failed", "urgent")]:
    q.add(tid, title, prio)
print([q.pop().ticket_id for _ in range(3)], q.pop())
